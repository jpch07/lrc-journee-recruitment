# Interactive management views in the Google Sheet backup

## Agreed outcome

Each successful manual Google Sheet backup publishes two polished, interactive tabs before the existing backup tabs:

1. **Results** — the Google Sheets equivalent of the interactive Excel management report and management Results view.
2. **Recruit Profiles** — the Google Sheets equivalent of the interactive Excel recruit profile and management Recruit Profile view.

Both tabs are view-only presentations of the same consistent backup snapshot. Selecting a dropdown changes only the spreadsheet view; it never writes back to Evalday. The combined scope contains completed Journees only. All remaining readable and technical backup tabs retain their current data, names, ordering relative to one another, restoration value, protections, and publication semantics. **Backup - Backup summary** becomes the third tab.

The live acceptance run and browser verification use the faster Oregon website. Virginia receives the same committed application release, but it is not the primary acceptance surface.

## Selected approach

Use a native Google Sheets presentation layer backed by raw, hidden helper ranges in the two presentation tabs. The application exports trusted layout metadata separately from literal snapshot values. The private standalone Apps Script applies formulas, dropdowns, formats, protected ranges, charts, and the selected profile image.

This is preferred over converting an `.xlsx` on every backup, which would be brittle and could create another Drive artifact, and over an Apps Script sidebar, which would no longer deliver the requested first two spreadsheet tabs.

The existing Excel management report remains the canonical presentation reference. Shared pure data builders should feed both Excel and Google renderers so ranks, labels, selector options, comments, notes, and profile breakdowns cannot drift.

## Tab 1: Results

The tab is named **Results** without the `Backup -` prefix. It uses the current management-report palette and typography: Aptos/Aptos Display where supported, navy title/header areas, white header text, pale alternating rows, configured performance-band colors, and green/yellow/red status treatment. Gridlines are hidden, selector/header rows are frozen, comments wrap, and widths and row heights follow the Excel report.

Selectors:

- `B3`: completed-Journee scope, defaulting to **All completed Journees**.
- `E3`: result view, defaulting to **Overall ranking**, followed by every configured dimension and activity.

The visible table mirrors the interactive Excel report: Rank, Recruit, Journee, Score, Scale, Details, Status, Color, General comment, and Notes. Every view sorts ranked rows by ascending relevant rank, then recruit name and Journee name; blank/unranked rows come last with the same deterministic tie-breakers. The all-completed overall view must not retain the current aggregate builder's incidental Journee grouping.

Raw values live in hidden columns and are written with `RAW` semantics so user-entered text can never become a formula. Only fixed formulas generated by application code may populate the visible table. Data validation restricts selectors to exported options. The sheet protects formulas and helper data while leaving only `B3` and `E3` editable.

## Tab 2: Recruit Profiles

The tab is named **Recruit Profiles** without the `Backup -` prefix. It uses the Excel report's yellow profile-tab identity, navy section headers, hidden gridlines, frozen selector/profile header, wrapped long text, and readable widths.

Selectors:

- `B3`: completed-Journee scope, defaulting to **All completed Journees**.
- `E3`: recruit selector, alphabetized and scoped to the selected Journee. A stable `journeyId:recruitId` key—not the display name—drives lookup. Labels remain deterministic and unique even when names repeat within one Journee; the Journee and a stable ordinal disambiguate them. When `B3` changes, the edit trigger resets `E3` to the first valid recruit in that scope before refreshing the profile, so a stale selection can never display another scope's data.

Changing either selector updates:

- Recruit photo, name, Journee/date, phone, date of birth, attendance, arrival and attendance comment.
- Overall score, all-completed rank, Journee rank, color grade, completion and missing components.
- Dimension scores/ranks/status/coverage and a radar chart.
- Activity scores/ranks/submission status and a radar chart.
- Dynamic general-assessment factors, average, general comment and notes.
- Evaluator breakdown, criterion-level grading and profile audit history.

Absent active recruits in completed Journees remain selectable and use the existing fallback-result behavior. Helper ranges are hidden and protected. Only `B3` and `E3` are editable.

### Dynamic selected photo

Google Sheets formulas cannot select an uploaded private binary image. The Recruit Profiles helper area therefore includes a protected, hidden, bounded preview store keyed by stable profile key. It contains the already-generated PNG thumbnail as numbered base64 chunks; it is presentation data, not a replacement for the original `_Photo bytes` restoration data. Preview chunks are written as literal values and checked for count, size and SHA-256 before layout publication.

The standalone script owns one installable spreadsheet edit trigger. It reacts only when `B3` or `E3` changes on the exact managed Recruit Profiles tab. The trigger resolves the stable selected profile key, reconstructs its verified PNG thumbnail from that tab's protected helper range, replaces only the managed profile image anchored in the profile-photo area, and performs no network request or write outside the fixed spreadsheet.

Publication inserts the initial selected photo. The trigger is installed idempotently by the explicit authorization/setup function: duplicate project triggers are removed before one replacement is created. Adding the trigger may require the spreadsheet owner to approve the script's updated scopes once. Trigger failure must not alter source data or technical backup integrity; the sheet should retain a clear placeholder/reference to **Backup - Photos** if the preview cannot be refreshed.

## Shared data and application changes

Extract shared, pure management-report payload builders from `app/report_exports.py`. They should expose completed Journees, combined and per-Journee result rows, selector labels/options, profile summaries, dimension/activity rows, evaluator/criterion/audit rows, and stable profile/photo keys. Existing `.xlsx` output continues to consume these builders and must remain byte-semantically equivalent in content and behavior.

For Google backup, the presentation payload is built inside the same existing consistent database snapshot as the technical records, or purely from objects captured inside that snapshot. It must not reopen a live `Session` after the snapshot closes. Photos may still be retrieved afterward as today, but the selected records, ranks, profile values and audit rows cannot diverge from the verified technical snapshot under concurrent edits.

`app/sheet_backup_export.py` prepends the two presentation tab descriptors and retains every current tab after them, except that the current basic readable Results tab is replaced by the richer Results presentation to avoid a duplicate. The existing Backup summary, database/readable tabs, Field details, Audit history, Photos, `_Records`, and `_Photo bytes` remain semantically unchanged.

Final titles are not arbitrary client input. The protocol allowlists exactly two unprefixed mappings—presentation `Results` to **Results** and presentation `Recruit Profiles` to **Recruit Profiles**—while every other managed tab keeps the existing `Backup - <name>` rule. Prepare and publish reject a non-backup-owned collision at either unprefixed title just as they already reject collisions at prefixed titles.

The export protocol gains one narrowly validated, versioned presentation-layout operation after literal rows and before verification/publication. It supports only the operations needed here:

- Fixed formulas and trusted array formulas.
- Merges, frozen rows/columns, hidden helper columns and gridline visibility.
- Fonts, fills, borders, alignment, wrapping, number formats, row heights, column widths and tab colors.
- Data validation sourced from bounded exported option ranges.
- Conditional formatting and the two radar charts.
- Protected sheet/range configuration that exposes only selector cells.

Presentation tabs may use up to a documented bounded column limit sufficient for their helper blocks; the current 60-column rule remains unchanged for all non-presentation tabs. Existing total-cell, request-size, batch-size, text-length and staging limits still apply.

`integrations/google-sheet-backup/Code.js` must reject unknown layout versions, formula targets, ranges, chart types, selector cells, tab names, sizes, and operations. It never accepts arbitrary Apps Script source or formulas from database/user content. Literal rows remain `RAW`; formulas originate only from the trusted layout generator.

Layout replay is deterministic and idempotent under the existing sequence/digest protocol. Before adding layout-owned charts, conditional-format rules, protections or profile images, the receiver removes or updates only objects carrying the expected managed metadata/known anchors and ranges. A lost response followed by replay must leave exact expected object counts, not duplicates.

## Publication and protection

The existing atomic staging and publish model remains intact:

1. Capture one consistent database snapshot.
2. Materialize literal rows and photos without holding the database transaction across Google calls.
3. Create and populate all staging tabs.
4. Verify all literal cell ranges, technical record reconstruction and original photo bytes exactly as today.
5. Apply the validated presentation layout to the two staging presentation tabs, including the initial selected profile image reconstructed from the verified hidden preview store.
6. Verify presentation selectors, fixed formulas/layout version, helper-row counts and expected chart/image counts.
7. Atomically replace the prior managed tab set and completion marker.

The trigger and selectors never bypass the backup's checksum/read-back gates. A layout, formula, chart or photo-preview failure prevents publication of the new snapshot; the previous complete backup remains available. A later selector-photo refresh failure affects only the presentation image and leaves verified data intact.

The existing unrelated `Sheet1` and any non-backup-owned sheet remain untouched. Technical and readable backup tabs keep their current whole-sheet protections and generic formatting. During presentation layout, the receiver locates its exact staging-sheet protection created during prepare and replaces it with one owned sheet protection whose only unprotected ranges are `B3` and `E3`. It never creates a transient wholly unprotected sheet and never changes non-owned protections.

## Security and privacy

The original backup security boundary is unchanged: no passwords, hashes, session tokens, secrets, credential-bearing URLs or cross-workspace records may enter either presentation tab or its helper ranges. The profile image trigger reads only previews already published by this backup in the fixed spreadsheet. It is constrained by managed sheet names/metadata and fixed selector cells, and ignores every other edit.

Because the destination's sharing permits link access, the existing personal-data warning remains authoritative. This work does not change sharing permissions.

## Testing

Automated tests cover:

- Shared Excel/Google payload parity, completed-Journee scoping, configurable dimensions/factors/terminology, absent recruits, duplicate names and deterministic ranked/unranked ordering for every selector view.
- Presentation rows remain consistent with the same technical snapshot under a concurrent source mutation.
- Exact first-two-tab order and names, with Backup summary third and all remaining tabs unchanged.
- Results selectors/defaults, visible columns/formulas, sorting, conditional formatting and protection boundaries.
- Profile selectors/defaults, stable lookup keys, summary sections, dynamic factors, evaluator/criterion/audit rows, charts and protection boundaries.
- Trusted-formula separation from literal cells and hostile formula-like user text.
- Receiver validation/rejection for malformed or oversized layouts, invalid ranges/formulas/charts/protection requests, final-title collisions, replay and retry behavior.
- Forced replay leaves exact chart, conditional-format, protection and image counts and never broadens editability beyond the two selectors.
- Trigger idempotent installation and edit filtering; initial image, selector-driven image replacement, duplicate-name selection and missing-photo placeholder.
- Existing export-size, batching, reconstruction, privacy, interruption and atomic-publication tests.
- Existing Excel management-report regression tests.

Live acceptance uses `https://evalday-oregon.onrender.com`:

1. Deploy the same exact commit to Oregon and Virginia and confirm both readiness endpoints.
2. Update and reauthorize the private standalone Apps Script, install exactly one edit trigger, and deploy its new version.
3. Start one real manual backup from Oregon and wait for read-back verification.
4. Confirm first-tab order and all existing backup tabs.
5. Change the Results scope and result view; verify values, sorting and formatting.
6. Change the profile Journee and recruit, including a duplicate-name case if available; verify all sections, charts and selected photo update.
7. Confirm selector cells are editable, formulas/helper ranges and technical tabs are protected, and no change writes back to the website.
8. Confirm the completion marker and Backup summary counts/checksum remain valid.

## Approved constraints

- Combined and selectable data use completed Journees only.
- The selected recruit photo must switch with the profile dropdown.
- Only the first two tabs become interactive; the rest remain as they are now.
- Oregon is the primary live testing surface because it is faster.
